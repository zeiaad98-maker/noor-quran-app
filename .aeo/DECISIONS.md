# v13.2 — DECISIONS

- Decision: Word = Quran.com wbw dedicated per-word MP3s, because the user changed his decision (13:25) after Muse explained honestly that no per-word files exist for Muallim/Tunaiji anywhere. The two-voice plan was discarded and fully reverted.
- Decision: Primary host audio.qurancdn.com (Quran.com's current CDN, per api-docs), old host verses.quran.com/wbw/ only as fallback if the new host fails — verified both return 200 on real files first.
- Decision: Reuse the existing cacheWbwFile path (v13) for cache-on-play — no new download machinery. No wbw files in assets, ever (Quran Foundation terms: redistribution/bundling needs written permission; streaming + on-device caching is the documented use).
- Decision: Mapping ground truth = Quran.com Verses API word text_uthmani vs our wordsForAyah() tokens, checked on 7 sample ayahs before shipping; any mismatch must be reported, not papered over. The token-based pause-mark rule was PROVEN WRONG (5,519 mismatches in 374 ayahs) — the mapping is a bundled shift table generated from the API's audio_urls (0 mismatches over 77,429 words). 36:52 word 7 (هَٰذَا) is a judgment call settled by duration (file 007 = 1.02 s vs file 008 = 0.65 s; known recordings 1.10–1.38 s) — flag for the user's ear.
- Decision: Fallback chain CHANGED (bug A, the user's #1 complaint): wbw → sheet error with retry. NO segment/ayah fallback — the segment subsystem was DELETED entirely (not demoted): `WordSegment`/`parseWordSegments`/`fetchWordSegments`/`wordSegmentsFor`/`wordVoiceReciterIndex`/bundled Husary loader in quran_audio.dart, the `word_segments_husary.json` asset + pubspec entry, `tool/fetch_husary_word_segments.py`, all segment tests, the QCF probe test. A word that cannot fetch its wbw file must NEVER play the ayah file.
- Decision: Meanings — مخلوف "كلمات القرآن: تفسير وبيان" is NOT in Dalail (verified 3 ways: title search, book search — only a critique of it, book 712 — author search 0). So the truncation fallback: غريب when present, else Raghib FIRST sentence (~120 chars, hard cap 160), with a clarity guard (first sentence a fragment < 25 chars → keep the next sentence/clause too, up to 160; skip citation clauses). Truncation only shortens, never rewrites; nothing invented. The user's condition ("اختصر وهيك بس يكون مفهوم المعنى") governs: clarity is the constraint, brevity serves it.
- Decision: Bug 1 root causes — (R1) stale-finish race: the old file kept playing during the new load's download await and its `completed` advanced the NEW queue; fixed by stopping old audio FIRST, a `_finishToken` (only the play that actually STARTED may finish), and a token-checked finally. (R2) 4 merged ayahs where QCF display words ≠ audio words (2:181, 8:6, 13:37, 37:130); fixed by `audioPositionForQcfWord` (both halves map to the shared audio position, later words shift down one).
- Decision: Bug 2 root causes — (R1) the same stale finish → `stop()` during a load invalidated it and the in-flight finally skipped clearing `isLoading`; (R2) explicit `stop()` during a load left the spinner up; fixed by `stop()` clearing `isLoading` itself (token-checked). (R3) `play()`/`setSpeed()` had no timeout — added (5 s / 10 s). (R4) the chain could take ~3 min — capped by a 60 s total `playBudget` that invalidates the attempt + reports the error. `isLoading` is cleared in exactly the token-guarded finally + `stop()` + the budget timer — never anywhere else.
- Decision: Bug B root causes — (B1) picking a count set the number while `repeatItem` stayed OFF; fixed: `setRepeatCount` enables repeat (count 1 = off). (B2) repeat settings were NOT persisted; fixed: SharedPreferences keys `audio_repeat_item`/`audio_repeat_scope`/`audio_repeat_count`/`audio_speed`, restored once by the reader at startup. (B3) no visible repeat state; fixed: remaining-plays line in the sheet + mini bar, shown only while a repeat play is running/loading. Manual next/prev/stop cancels repeat immediately (best-apps rule 3).
- Decision: Bug C — NO playback highlighting existed (verseBackgroundColor only marks noted ayahs). Implemented: the QCF page colours the playing ayah (pale amber tint) + the playing word (stronger amber + dark-amber word colour), cleared on stop/pause, toggleable in reader settings (`highlight_playback`, default true). Word scope colours the word; ayah/page/surah scope tints the whole ayah.
- Decision: UX D / best-apps rules 2+6 — tap a word plays JUST the word immediately + opens the word card + shows the mini bar; the card carries a prominent full-width "استمع للآية" button (the visible ayah-listen control); long-press on a word plays its ayah (a separate, explicit gesture — nested-span recognizers, the gesture arena disambiguates tap vs hold). The ۝ ornament still opens the tafsir card. Tap-on-ayah-text playing the ayah is an improvement over all references and exactly what the user asked for — implemented as tap-word-plays-word + card button + long-press.
- Decision: Loading (rule 5) — reciter downloads already showed a progress bar; added the missing Cancel button (`service.cancel()`). Audio loads are time-boxed per step + the 60 s budget; failure = explicit error + retry, never an endless spinner.
- Decision: Fake just_audio gains a load-delay hook + `emitCompleted()` injector for the race/budget tests, and `playBudget` is a mutable static so tests can shorten it — test-only changes, no production behavior change.
- Decision: Ayah audio needs NO change — verified only: 7 real Tunaiji everyayah files, all complete per-ayah files (HTTP 200, ffmpeg decode clean, natural fade, no abrupt ends).
